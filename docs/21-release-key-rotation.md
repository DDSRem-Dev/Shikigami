# 发行签名密钥轮换与撤信演练

本页补充[发行流程](18-release-readiness.md#github-actions-自动构建签名与发布)的操作验收，不改变[安装信任契约](11-automated-installation.md#本地离线签名与验签)。2026-10-29已完成使用临时测试密钥的本地离线演练；真实发行私钥、仓库公钥、GitHub Secret/Variable、受保护tag和公开Release均未操作。当前工具没有在线撤销查询、集中信任库或可信签名时间戳。

## 可重复执行的入口

```bash
python3 -B scripts/test-release-key-rotation.py \
  --evidence /private/tmp/shiki-key-rotation-new-evidence
```

输出目录必须不存在。入口从可信仓库构建`release-trust`，也可显式传入从可信源码预编译的`--verifier`；两种方式均需要Go，以编译仅使用标准库的临时密钥生成器。`--go`可指定Go可执行文件。构建串行且限制`GOMAXPROCS=2`、`-p=1`，不依赖系统OpenSSL/LibreSSL的算法版本。

脚本只生成两把全新临时Ed25519密钥，不接受真实私钥参数，也不调用GitHub、下载发行归档、服务管理或任何包内程序。测试版本`v0.0.0-alpha.1`和`v0.0.0-alpha.2`为含14个标准成员的微型惰性归档，按发布工具核对成员、版本、payload hash及pin；它们不是可安装产品或实际Release。私钥位于独占0700临时目录，文件0600；正常完成和异常退出均由临时目录上下文清理。公开测试密钥、归档、签名、成功回执及JSON汇总保留为证据。清理不等于磁盘安全擦除；SIGKILL/掉电后的强制终止清理未由此演练证明。

## 实际验证的12步

| 步骤 | 结果 |
|---|---|
| 旧测试密钥签旧版本 | 成功，创建新签名文件 |
| 轮换前调用方选择旧公钥 | 验签及私有认证副本成功 |
| 新测试密钥签新版本 | 成功 |
| 调用方将本次测试的当前公钥替换为新公钥 | 新版本认证成功，回执指纹为新公钥 |
| 当前新公钥验证旧版本旧签名 | 拒绝，无输出目录或成功回执 |
| 显式旧公钥验证新密钥签名 | 拒绝，无成功产物 |
| 明确选择归档的旧公钥验证原旧版本 | 成功，证明计划轮换后的历史校验可保留 |
| 模拟被撤信旧密钥继续签新版本 | 数学上仍可签名，产生独立测试签名 |
| 当前新公钥验证上述旧密钥签名 | 拒绝 |
| 调用方继续显式选择旧公钥验证上述签名 | 仍能认证，明确暴露离线工具的撤销边界 |
| 移除本次测试的旧私钥后尝试签名 | 拒绝，未创建签名文件 |
| 移除本次测试的当前公钥后尝试验签 | 拒绝，未生成认证副本或回执 |

所有正例还核对公钥指纹、完整归档SHA-256、私有副本内容与落盘回执；负例要求退出1且不发布成功输出。输入归档/sidecar和公开测试密钥后置hash保持一致。

“当前公钥替换”只是本次调用方选择的本地文件变化，不是产品新增的信任库。移除临时私钥只证明该路径不能继续签名，不声称已有密钥副本失效，也不等同已在GitHub停用真实Secret。

## 计划轮换与泄露处置的区别

计划轮换时，在受信渠道确认新公钥指纹，协调仓库公钥与签名环境Secret/Variable，使下一版本tag固定相应身份；保留旧公钥用于已知历史版本校验。既有版本tag和Release资产不覆盖，自动发布的公钥匹配检查仍必须通过。不能仅从待验归档旁取得公钥就建立初始信任。

若旧私钥泄露，应暂停发行并停用相应签名凭据，通过受信渠道明确公布受影响的指纹、版本与新密钥，更新调用方信任选择。旧密钥签名没有可信时间戳，单靠签名不能区分“泄露前正常签名”和“泄露后伪造”：本演练已明确验证继续指定旧公钥仍会成功。不能将保留的旧公钥当作泄露后所有旧签名都安全的依据；历史例外需要此前独立保存的可信固定归档摘要和明确处置政策，否则保持拒绝。当前工具不提供自动通知或在线撤销机制，不应宣称全局即时撤销。

本批没有实际轮换或撤销生产身份。正式操作仍需按当时授权及发行环境执行并留存证据，不能把本页的隔离验收写成已在GitHub移除真实密钥。
